# 第一幕铁甲战士复刻：团队开发计划与验收标准

版本：1.0  
适用技术：C++17、SFML 3.0.1、CMake、Visual Studio 2022  
团队规模：5人

## 1. 项目目标

本项目不是完整复刻《杀戮尖塔》的全部内容，而是实现一局具有完整流程的“第一幕铁甲战士体验”。

最终流程必须完整连通：

```text
主菜单
→ 新游戏/继续游戏
→ 初始事件
→ 第一幕路线地图
→ 普通战斗、问号、商店、宝箱、篝火、精英
→ 战斗奖励和卡牌选择
→ Boss前篝火
→ 第一幕Boss
→ Boss奖励/第一幕结算
```

“体验接近原作”指核心玩法、房间类型和决策循环接近原作，不要求复制原作源代码、画面、全部数值或全部美术资源。

原作内部源码并未作为本项目依据。本文引用社区资料核实原作行为，代码架构由本团队自行设计。

## 2. 原作行为基线

根据社区资料，第一幕共有17层：第1层固定普通战斗，第9层固定宝箱，第15层固定篝火，第16层为Boss，第17层为Boss宝箱。

地图具有以下节点：

- 普通战斗
- 精英战斗
- 问号房间
- 商店
- 宝箱
- 篝火
- Boss

问号房间进入后可能解析为事件、普通战斗、商店或宝箱。篝火默认提供休息和升级，且只能选择一种。

铁甲战士基础状态：

- 最大生命：80
- 初始牌组：5张打击、4张防御、1张痛击
- 初始遗物：燃烧之血，战斗结束恢复6点生命
- 每回合基础能量：3
- 每回合基础抽牌：5

第一幕敌人内容基线：

- 普通敌人族：邪教徒、下颚虫、虱虫、酸液史莱姆、尖刺史莱姆、真菌兽、哥布林、盗贼、蓝奴隶、红奴隶
- 精英：地精大块头、乐加维林、三哨卫
- Boss：守护者、六火亡魂、史莱姆老大

铁甲战士原作卡池约75张（含基础打击、防御和痛击），且每张牌有升级形态。全部实现是最终内容目标，不是第一阶段目标。

## 3. 范围分级

项目采用两级目标。必须先通过P0，再扩充P1。不能在P0未打通时大量添加卡牌和美术。

P0必须具备完整一局，不允许缺少场景而使用控制台代替：

- 17层固定规则地图，并且至少有3条可选路线
- 所有7类节点都可进入并正确返回地图
- 25张可用铁甲战士卡牌，均有升级形态
- 抽牌堆、手牌、弃牌堆、消耗堆
- 攻击、技能、能力牌
- 力量、敏捷、虚弱、易伤、脆弱、金属化、仪式、眩晕等必要状态
- 至少6种普通战斗组合
- 3种精英全部实现
- 1个完整Boss
- 至少6个第一幕事件
- 商店：购买卡牌、遗物、药水和删牌
- 篝火：休息和升级
- 宝箱：获得遗物
- 战斗奖励：金币、三选一卡牌、跳过
- 至少12个遗物，包括燃烧之血
- 至少8种药水
- 存档/读档
- 主菜单、地图、战斗、奖励、事件、商店、篝火、宝箱、结算界面
- Release版本可在没有SFML和Visual Studio的Windows x64电脑直接运行

### 3.2 P1：最终完整目标

P0稳定以后，再完成：

- 75张铁甲战士卡牌及升级形态
- 第一幕全部普通敌人族和主要组合
- 3个精英
- 3个Boss，开局随机确定本局Boss
- 12个第一幕专属事件，加至少6个通用事件
- 至少25个适用于铁甲战士的遗物
- 至少12种药水
- 随机地图生成，满足固定层规则和可达性约束
- 敌人、卡牌和事件数据外部配置
- 基础动画、音效、悬停信息和战斗日志

不在本项目范围：

- 第二幕及以后内容
- 其他角色
- 每日挑战、进阶模式、成就和排行榜
- 云存档和联网
- 完全复刻原作所有遗物、药水、事件和概率
- 复制或公开分发原作受版权保护的素材

## 5. 公共数据所有权

一个数据只能有一个真实所有者，UI不得复制一份独立数据作为真实状态。

| 数据 | 所有者 | 可读取者 |
|---|---|---|
| 当前生命、最大生命、金币、长期牌组、遗物、药水、当前节点 | A的`RunState` | B/C/D/E |
| 单场能量、格挡、手牌、抽牌堆、弃牌堆、消耗堆 | B的`CombatSystem` | A/C |
| 卡牌定义、升级数据、效果描述 | A的`CardDatabase` | B/C/E |
| 敌人血量、格挡、状态、攻击意图 | B的`Enemy` | C |
| 地图节点、连线、已访问状态 | D的`MapState` | A/C |
| 事件定义、选项和事件结果 | E的`EventSystem` | A/C |
| 当前场景 | A的`Game`/`SceneManager` | C |
| 界面坐标、悬停、选中状态、动画状态 | C的UI对象 | C |

典型规则：

- C只读取敌人血量并画血条，不直接修改血量。
- A描述卡牌效果，B在战斗中执行效果。
- D决定地图节点和路线；E决定问号事件内容。
- A以组长身份负责场景切换，不在`Game`里重复实现卡牌、战斗、地图或事件规则。

### 7.2 卡牌模型

禁止只使用`damage`和`block`两个字段表示全部卡牌。建议使用组合效果：

```cpp
enum class CardType { Attack, Skill, Power, Status, Curse };
enum class CardTarget { None, Self, SingleEnemy, AllEnemies };

enum class EffectType
{
    Damage,
    GainBlock,
    DrawCards,
    GainEnergy,
    LoseHealth,
    ApplyPower,
    ExhaustCard,
    AddCardToDrawPile,
    AddCardToDiscardPile
};

struct CardEffect
{
    EffectType type;
    int value;
    std::string parameter;
};

struct CardDefinition
{
    std::string id;
    std::string name;
    CardType type;
    CardTarget target;
    int cost;
    std::vector<CardEffect> effects;
};

struct CardInstance
{
    std::string definitionId;
    bool upgraded = false;
};
```

复杂卡牌允许使用注册函数，不能为了数据驱动写大量难以维护的字符串判断。

```cpp
class CombatSystem
{
public:
    void startBattle(const EncounterDefinition& encounter,
                     const RunState& runState);
```

## 10. 成员D与E：地图、事件与非战斗房间

### 10.1 最终责任

D负责地图结构，E负责事件内容，C负责房间画面，A以组长身份负责切换场景、保存状态并协调业务接口。商店、篝火、宝箱涉及卡牌时调用A的卡牌模块公开接口。

### 10.2 地图规则

P0允许使用经过验证的固定拓扑，但节点内容应具有随机性。P1再实现随机拓扑。

必须满足：

- 至少一条从起点到Boss的路线
- 第1层固定普通战斗
- 第9层固定宝箱
- 第15层固定篝火
- 第16层固定Boss
- 玩家只能选择当前节点连接的下一节点
- 已完成节点不能重复领取奖励
- 同一种子生成同一地图和房间结果

### 10.3 问号与事件

问号先解析为：

```cpp
enum class UnknownRoomResult
{
    Event,
    Monster,
    Treasure,
    Shop
};
```

事件统一模型：

```cpp
struct EventOption
{
    std::string text;
    std::vector<RunEffect> effects;
    EventCondition condition;
};

struct EventDefinition
{
    std::string id;
    std::string title;
    std::string description;
    std::vector<EventOption> options;
};
```

#### D/E-M2：三种非战斗房间

- 篝火：休息30%最大生命或升级一张牌
- 宝箱：获得一个遗物
- 商店：卡牌、遗物、药水、删牌和金币检查

验收：金币不足不能购买；同一商品不能重复购买；篝火一次只能选择一项。

#### E-M3：P0事件与问号

- 问号解析
- 至少6个第一幕事件
- 事件条件、选项和结果
- 事件不能通过反复读档重新随机

验收：同一种子和相同访问顺序得到相同事件；所有选项不会导致生命超过最大值或金币非法。

#### E-M4：第一幕完整内容

- 12个第一幕专属事件
- 至少6个通用事件
- D完成随机地图拓扑
- 房间和事件权重
- 初始事件和Boss确定

验收：生成1000张地图，全部可到达Boss并满足固定层约束。

## 11. 模块交互流程

### 11.1 打出一张攻击牌

```text
A提供卡牌定义
→ C检测点击和目标
→ C调用B的playCard(handIndex, enemyIndex)
→ B检查能量并执行效果
→ B修改敌人血量和牌堆
→ C重新读取战斗状态并绘制
```

### 11.2 点击地图问号

```text
C报告点击的节点ID
→ D检查是否可达
→ E解析问号结果
→ A的核心模块切换到对应场景
→ 若为事件，E提供事件内容，C显示选项
→ E通过A公开的RunState方法应用结果
→ A返回地图场景
```

### 11.3 战斗胜利

```text
B产生战斗结果
→ A写回生命和金币
→ A触发燃烧之血等战后遗物
→ A生成卡牌奖励
→ C显示三选一和跳过
→ A将选择写入长期牌组
→ D标记节点完成
→ A返回地图
```

### 11.4 篝火升级

```text
E提供休息/升级选项数据
→ C显示牌组
→ 玩家选择卡牌
→ A验证卡牌可升级
→ A更新RunState中的CardInstance
→ D标记篝火完成
→ A返回地图
```

## 12. 八阶段总进度

每个阶段建议为一周；如果课程时间更短，可以压缩日期，但阶段顺序不能颠倒。

| 阶段 | 全组目标 | A（组长） | B | C | D | E |
|---|---|---|---|---|---|---|
| M0 | 接口冻结 | 目录/CMake/RunState/卡牌模型 | 战斗接口 | UI输入接口 | 地图接口 | 事件接口/资源规范 |
| M1 | 单场战斗 | Game与场景/基础10张牌 | 邪教徒基础战斗 | 战斗占位UI | 固定地图原型 | 事件数据模板/占位资源 |
| M2 | 战斗完整 | 资源/随机数/P0共25张牌 | 多敌人/状态 | 完整战斗交互 | 节点与路线规则 | 3个事件/资源清单 |
| M3 | 地图闭环 | 跨场景状态/卡牌奖励 | 6普通战斗 | 地图/事件/奖励UI | 地图选择与可达性 | 问号解析和6个事件 |
| M4 | P0精英Boss | 战后触发/失败/复杂牌测试 | 3精英+1Boss | 全部场景可用 | 固定楼层约束测试 | 事件条件与结果测试 |

### 阶段门禁

- M1结束：必须能打完一场邪教徒战斗。
- M3结束：必须能从地图进入房间并返回，状态不丢失。
- M5结束：必须能从新游戏一直打到Boss结算。
- M6之后：只允许补内容、修错误和改善表现，不再重构公共接口。

## 13. 测试责任

测试不是某一个人的工作，每个人负责自己模块的测试。

### A测试（组长、核心与卡牌）

- 场景切换
- RunState边界
- 存档往返一致性
- 同种子可重复
- Release资源路径
- 卡牌ID唯一
- 升级前后数据
- 奖励稀有度
- 每种特殊卡牌效果

### B测试

- 伤害、格挡、虚弱、易伤
- 能量不足禁止出牌
- 牌堆洗牌和手牌上限
- 敌人行动序列
- Boss阶段转换

### C测试

- 点击边界
- 不同窗口尺寸
- 长文本换行
- 空列表和最大手牌
- 所有场景可通过鼠标完成

### D测试

- 地图可达性
- 固定楼层约束
- 节点连线与可选状态
- 访问后节点状态

### E测试

- 事件条件和结果
- 事件选项只可执行一次
- 事件数据缺失或非法时的回退
- 商品购买与删牌的协作流程
- 篝火只能选择一次

### 全组回归

每次合并到`main`后至少执行：

```text
Debug构建
启动新游戏
进入一次战斗
打出一张攻击牌和防御牌
结束回合
胜利后选择奖励
返回地图
保存并读档
```

```text
feature/game-core
```

```text

如何测试
测试结果

```

合并条件：

- Debug构建通过
- 新增`.cpp`已加入CMake
- 没有提交`out/`、`.vs/`、EXE、DLL、OBJ、PDB和日志
- 没有个人绝对路径

- 至少一名其他成员检查
- 公共接口变更得到相关负责人确认

## 15. 完成定义

一个功能只有同时满足以下条件才算完成：

- 正常路径可以使用
- 非法输入不会崩溃
- 界面能展示结果
- 状态可以正确保存或回到地图
- 有自动测试或明确的人工验收步骤
- Debug构建无错误
- 代码已经通过PR合入`main`
- 文档与实际行为一致

## 16. 最终答辩验收

答辩版本必须能够演示：

1. 从主菜单开始新游戏。
2. 展示铁甲战士初始牌组和燃烧之血。
3. 在地图上选择不同路线。
4. 完成一场普通战斗，展示抽牌、能量、格挡、状态和意图。
5. 选择或跳过卡牌奖励。
6. 进入一次问号并完成选择。
7. 在篝火休息或升级卡牌。
8. 在商店购买或删除卡牌。
9. 击败一个精英并获得遗物。
10. 保存、退出并继续游戏。
11. 击败第一幕Boss并进入结算。

发布目录至少包含：

```text
SlayTheSpire.exe
SFML运行时DLL
assets/
README.txt
```

必须提前在一台没有安装Visual Studio和SFML的Windows x64电脑测试。答辩同时准备Release压缩包、U盘备份、网盘备份和完整流程录屏。
