## 项目上下文摘要（篝火休息房与商店）

生成时间：2026-09-02 00:00:00

### 1. 相似实现分析

- **实现1**: `src/app/Game.cpp`
  - 模式：`Game` 统一做场景切换、点击分发和返回地图。
  - 可复用：`SceneType`、`handleWindowEvent()`、`showMap()`、`startBattle()`。
  - 需注意：新增房间场景后，不能破坏地图上的路线限制和事件访问记录。
- **实现2**: `src/ui/EventView.cpp`
  - 模式：界面层只做绘制、命中检测和状态切换，不直接碰渲染外的逻辑。
  - 可复用：资源加载、按钮布局、浮动文字和返回地图的时机控制。
  - 需注意：商店需要独立的点击区域和购买结算，不应把规则写进绘制函数里。
- **实现3**: `src/ui/BattleView.cpp`
  - 模式：用固定逻辑分辨率布局卡片和按钮，点击只转成规则调用。
  - 可复用：`CardView`、`UiHelpers`、固定尺寸卡片排版方式。
  - 需注意：商店卡牌区也应使用固定网格，避免和窗口缩放互相打架。

### 2. 项目约定

- **命名约定**: 类型大驼峰，函数和变量小驼峰，常量 `k` 前缀。
- **文件组织**: `src/app/` 管流程，`src/ui/` 管界面，新增房间逻辑适合放 `src/room/`。
- **导入顺序**: 本模块头文件、项目内头文件、第三方头文件、标准库头文件。
- **代码风格**: C++17、SFML 3.0.1、界面功能按场景拆分，背景可以先占位。

### 3. 可复用组件清单

- `src/core/GameState.hpp`: 生命、金币、牌组、事件访问记录。
- `src/card/CardDatabase.cpp`: 可售卡牌来源。
- `src/relic/RelicDatabase.cpp`: 可售遗物来源。
- `src/relic/RelicSystem.cpp`: 遗物拾取结算。
- `src/ui/CardView.cpp`: 卡牌绘制。
- `src/ui/UiHelpers.cpp`: 按钮和居中文本。

### 4. 测试策略

- **测试框架**: 现有 CMake + `tests/*.cpp`。
- **测试模式**: 为新的房间规则补一组小型单元测试，再做 Debug 构建和短启动。
- **覆盖要求**: 篝火回血数值、商店商品数量、购买扣费、删牌扣费和返回地图流程。

### 5. 依赖和集成点

- **外部依赖**: SFML Graphics。
- **内部依赖**: `Game` 接收地图节点类型，切换到休息或商店场景；商店结算调用 `GameState`、`CardDatabase`、`RelicDatabase` 和 `RelicSystem`。
- **集成方式**: 地图点击进入房间，房间操作完成后回到地图。
- **配置来源**: `CMakeLists.txt` 需要加入新增 `.cpp`。

### 6. 技术选型理由

- **为什么用这个方案**: 先用纯功能和占位背景把房间流转打通，再单独替换美术资源。
- **优势**: 逻辑层和 UI 层可以分开测，商店库存也能复用数据表。
- **劣势和风险**: 商店删除卡牌需要额外的选牌交互，处理不好容易把 UI 和规则耦死。

### 7. 关键风险点

- **边界条件**: 金币不足、卡牌卖完、遗物已购、牌组为空时删牌都要有提示。
- **性能瓶颈**: 商店资源规模很小，随机生成一次即可。
- **规则风险**: 已购买遗物要走 `RelicSystem` 的拾取逻辑，不能只改名字不改状态。
